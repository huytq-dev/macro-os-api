# Mutation → dependency matrix and freshness contract (BE, 2026-10-23)

Scope: BE side of "full real-time data synchronization". Code reading only (no API start, no prod DB, no migration). Paths are under `BE/src`. Nothing here changes a business rule, API contract or schema; proposals are in §6 and need the user's approval.

## 0. Pipeline in one paragraph
Source write is saved first (`uow.EnsureSaveAsync`), then `DerivedDataSync.RunAsync` (`Application/Features/DerivedData/DerivedDataSync.cs:28-79`) tries, **inside the request**, to rebuild the derived data under a per-user app lock (`sp_getapplock`, `UnitOfWork.cs:35-43`): refresh `NutritionDayAggregate` of the touched days (`:55`) → `ExpenditureRebuilder.RebuildAsync` (daily progress + expenditure snapshots, `:59`) → commit. Anything it cannot finish in the request (lock not obtained within `DerivedLockWaitMs` 3000 ms `:46`, row budget `DerivedSyncRowBudget` 300 reached `:61`, exception `:69-77`, budget 0 `:35`) becomes a **durable `RecalculationJob`** (`DerivedDataJobs.EnqueueAsync`, `DerivedDataJobs.cs:17-36`), merged into any existing Pending job (union of dates), and the worker is woken (`uow.Derived.Wake()`). The worker (`Infrastructure/Implementations/Services/DerivedDataWorker.cs:20-69`) polls every `DerivedWorkerPollSeconds` = 10 s, claims jobs with a conditional UPDATE (`:81-88`), re-reads the source **after** taking the same user lock (`DerivedDataJobs.cs:42-73`) and marks every merged job Succeeded in the same transaction as the snapshots.
Result: after any mutation response, **source data is committed**; derived data is either already fresh (`RunAsync` returned true) or a Pending/Running job exists and `GET /api/derived-data/status` says `Updating`.

## 1. Mutation matrix
Columns: **Sync** = written in the same request/transaction before the response; **Derived** = goes through `DerivedDataSync` (sync attempt + job fallback); **Reads that change** = GET endpoints whose answer changes. "Live" reads query the source tables and are correct as soon as the mutation returns; "Derived" reads use snapshots/aggregates and are only correct when status = Ready (§2).

## 3. Freshness contract today and the "old job must not overwrite newer data" audit
### 3.1 What is exposed
- `GET /api/derived-data/status` → `{ state: Ready|Updating|Failed, fromDate, toDate, attempt, updatedAt }` (`Contract/Models/DerivedData/DerivedDataStatusResponse.cs:12`, computed by `DerivedDataJobs.StatusAsync`, `DerivedDataJobs.cs:76-96`). `Updating` = any job Pending/Running/Failed-with-attempts-left; `Failed` = a job reached `DerivedJobMaxAttempts` (5); `Ready` = no open job (`updatedAt` = last Succeeded job time, or null).
- **No read endpoint carries a freshness marker.** A grep of `Contract/Models` finds no `AlgorithmVersion`, revision or calculated-through field on any derived response. `ExpenditureSnapshot.AlgorithmVersion`, `RecalculationJob.AlgorithmVersion` and `NutritionDayAggregate.LastCalculatedAt` exist in the database only.
- Mutation responses do **not** say whether the sync rebuild completed (`DerivedDataSync.RunAsync` returns bool, every caller drops it, e.g. `FoodLogSupport.cs:180`). FE must ask the status endpoint.

### 3.2 Protections that exist (verified)
| Protection | Where | Verdict |
|---|---|---|
| One rebuild per user at a time (app lock) | `DerivedDataSync.cs:46`, `DerivedDataJobs.cs:45`, `SetExpenditureModeCommandHandler.cs:18` | sound for every writer that takes it (G4 lists the two that do not) |
| Job re-reads the source **after** the lock | `DerivedDataJobs.cs:42-73` (comment `:5`) | a late/old job recomputes from the newest source, so it cannot reintroduce old numbers |
| Claim = conditional UPDATE, loser gets 0 rows | `DerivedDataWorker.cs:81-88` | safe with two instances (local + MonsterASP) |
| Busy lock ⇒ job released to Pending without consuming an attempt | `DerivedDataWorker.cs:93`, `ReleaseAsync` | ok; release colliding with a Pending duplicate handled since G20 |
| Dead worker: Running job older than `DerivedJobLeaseSeconds` (300) is re-claimed | `DerivedDataWorker.cs:52-54` | ok |
| Failed jobs retried with 10·2ⁿ s back-off up to 5 attempts | `DerivedDataWorker.cs:54,59` | ok |
| Snapshot written by a **newer** `AlgorithmVersion` is never overwritten by an older build | `ExpenditureRebuilder.cs:115-121`, `AlgorithmVersions.IsNewer` | ok. **Bug G1 fixed** (below): this guard used to skip the daily-progress update as well |
| Merged pending jobs: union of dates | `DerivedDataJobs.cs:29-34` | ok |

## 4. Rules for MOS-FE (exact)
1. **After every successful mutation in §1 with a Derived column**: immediately invalidate the **Live** reads of that feature (food log day/week, weights/trend, water, nutrients day, macro series, goals progress, programs/current).
2. **State comes with the mutation response (P1, implemented):** every successful (2xx) POST/PUT/PATCH/DELETE of a logged-in user, except `/api/auth/*` and `/api/derived-data/*`, carries the response header `X-Derived-Data-State: Ready | Updating | Failed` (same value as `GET /api/derived-data/status`; CORS exposes it via `Access-Control-Expose-Headers`; `API/Filters/DerivedDataStateFilter.cs`). Read the header instead of calling the status endpoint. If the header is missing (older BE build, error response, reading failed) fall back to one `GET /api/derived-data/status`. The header is present on mutations with no derived effect too (it then just reports any other open job).
   Then act on the state (the fallback `GET /api/derived-data/status` returns the same three values, one indexed query):
   - `Ready` → invalidate the **Derived** reads (§2: expenditure*, energy-balance*, expenditure/daily, check-ins*, nutrition overview, nutrient series). Done.
   - `Updating` → keep showing the last value but mark Derived reads **stale** ("updating", never as fresh). Poll the status: 1 s, 2 s, 3 s, then every 5 s; stop at `Ready`, `Failed`, a new mutation (restart) or 3 minutes (5 job attempts with back-off take about 2.5 min; lease is 5 min). On `Ready` invalidate the Derived reads once.
   - `Failed` → show an error state on Derived reads with a retry button calling `POST /api/derived-data/retry`, then poll again as above. Never display a Failed state's numbers as fresh.
3. Mutations with **no** Derived effect (steps, body metrics, notes, settings, favorites, recipes, custom foods, shortcuts, layout, photos, periods, nutrient targets/pins, **water**, profile) need only rule 1; do not poll. After check-in accept/reject, goal/program edits and manual TDEE/reset also refetch `/programs/current`, `/goals/*`, `/expenditure*` and `/expenditure/daily` (targets are recomputed on read).
4. A 409 from a write on a RowVersion table (food-log PUT and others) = another request won; refetch the Live read and let the user retry. The BE already retries idempotent writes once.
5. Do **not** try to make Expenditure move after each food: while the status machine is Calibrating/Holding, or data are insufficient, the TDEE legitimately stays the same (`ExpenditureStatusMachine`, `ExpenditureRebuilder.cs:123-134`). `Ready` + unchanged TDEE is correct, not stale.
6. Do not call the status endpoint on a timer when nothing was mutated; one call on app foreground / route focus is enough.
7. No version or revision value is available to compare against (§3.1); use the status state only. If the product wants a per-response marker, see §6.
